Why curl one-liners caught on

Max Howell · November 4, 2026

A tool that is never installed can never succeed. That is why I introduced a one-line installer for Homebrew, and why I still think the compromise made sense.

Curl one-liners still upset people. You offer a command to paste into a terminal, and someone asks for a proper installer. Preferably a .pkg. Something respectable.

There are good reasons to prefer that package. There are also good reasons the one-liner caught on. Both deserve a better explanation than “never pipe curl into a shell.”

Getting from interested to installed

When I created Homebrew in 2009, installation was the problem I was trying to make disappear. Dependencies, build tools, files in the right directories: the work between wanting some software and actually using it.

Homebrew itself needed to cross that gap. A package manager has an awkward first dependency: you have to install the package manager.

The one-line installer made that first step small. Copy. Paste. Return. Let the computer do the tedious part.

The familiar shorthand is curl | sh, though the precise interpreter and syntax vary. The idea is to fetch an installer and execute it in one command. Homebrew still offers that experience today.

That convenience matters most when someone is merely curious. They have not yet decided your tool is worth their afternoon. Give them a page of prerequisites and manual setup, and you may never get the chance to demonstrate that it is.

The enduring popularity of the one-liner tells me the compromise met a real need. It does not prove it is the safest option, or the best option for every machine. It shows that people value getting started enough to accept some tradeoffs. Sometimes convenience wins.

What the security objection gets right

A package can execute code during installation too. Apple explicitly supports custom installation code in a .pkg. Putting a script inside an installer does not make its author benevolent.

But a signed package adds something important: a way to verify who signed the artifact and whether it has changed. In the normal macOS download-and-open flow, Gatekeeper checks developer identity, integrity, and notarization. Those are real protections.

This is the distinction that “I trust the vendor” can miss. I can trust the developer and still receive malicious bytes from a compromised download server. If the attacker cannot produce a signature from the expected publisher, signature verification can catch that substitution. An ordinary curl-to-shell command has no equivalent check. HTTPS protects the connection; it does not make a compromised endpoint honest.

Inspection is another difference. Reading a script in your browser and then fetching it again to execute does not guarantee you run what you read. The response can change between requests, or differ by client. Downloading once, inspecting that file, and executing that same file closes that particular gap. If the script fetches more code, you still have more to verify.

Nor does every installed program have the same authority. A sandboxed app, a command running as your user, and an installer running as root have different reach. macOS also restricts access to protected data through TCC. Signing, sandboxing, and privacy permissions are distinct mechanisms; a signature alone is not a sandbox. “It can run code” does not mean “it can do whatever it wants.”

So yes: a typical curl one-liner gives up protections that other installation paths can provide. Calling every objection superstition would be wrong.

The compromise I still defend

Once you have established that you are receiving the vendor’s actual code, and compared the permissions it will have, the underlying decision becomes familiar: do you trust this software enough to run it?

A signature helps establish provenance. It does not promise that the software is wise, harmless, or free of bugs. A friendly installer window cannot make that promise either.

For a developer trying a command-line tool from a vendor they trust, a one-liner can be a reasonable choice. For a managed fleet or a production build, reproducible versions and verified artifacts may matter much more than shaving a minute off setup. Those are different circumstances, not a contradiction.

I would make the convenience tradeoff again. I would also offer other installation methods. The quick path should help someone try your thing; it should not force everyone to accept the same policy for installing it.

What I would ship today

The irony is that many tools need less installation machinery now.

The problem Homebrew addressed involved source trees, libraries, dependencies, and files scattered across a filesystem. Plenty of software still looks like that. But for many modern command-line tools, the deliverable is a single executable. Installation can be as simple as putting the right binary somewhere on PATH.

If that describes your tool, consider whether you need an installer script at all. For a release archive containing one executable at its root, the basic operation looks like this:

mkdir -p "$HOME/.local/bin"
curl -fsSL https://example.com/tool-v1.2.3-PLATFORM.tar.gz \
  | tar -xz -f - -C "$HOME/.local/bin" tool

That is an illustrative URL: substitute the release for the user’s operating system and architecture. The archive must contain an executable named tool with executable permissions, and ~/.local/bin needs to be on PATH. The -f - tells tar to read the archive from standard input.

This avoids executing a downloaded installer script. It does not authenticate the binary, make arbitrary archives safe, or prevent a failed download from leaving a partial installation. For a verified installation, download to a temporary location, check the signature or attestation against the expected publisher, then extract and install the verified artifact. A checksum is useful only to the extent that you trust where you got the expected checksum.

Offer a package-manager route where one makes sense, and signed, notarized distribution on macOS. Publish direct, versioned downloads. Make updates and removal straightforward. If a bootstrap script still earns its place by selecting the platform or handling setup, keep its job small and avoid asking for elevated privileges unnecessarily.

Packslip is worth a look here. Its installation options include package managers, direct downloads, and a short shell installer. It also provides release verification. The shell installer checks its downloaded executable against a digest embedded in the script, and the script itself can be downloaded and verified through a GitHub attestation. Piping the live script straight into a shell still means trusting that initial download; verification has to happen before execution to protect that step.

That is the direction I want installation to take: fewer moving parts, verifiable releases, and a first step small enough that people will actually take it.

I still want you to be able to try the thing. These days, we can often make that easier without asking quite so much trust along the way.
